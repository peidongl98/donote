## 一、改了什么

### 判据

| 操作 | 改造前 | 改造后 |
|---|---|---|
| 列表 | 每次都发 PROPFIND，等网络回来才渲染 | 本地索引里已有这一层 → **立刻返回**，同时在后台发 PROPFIND 对账 |
| 打开笔记 | 有副本先给副本（已经是这样） | 不变；校验改用 **etag**（原来只有 mtime） |
| 回收站列表 | `1 + N` 次请求（列目录 + 逐篇 GET 正文） | 列目录走缓存；正文走**软删时留下的本地副本** |
| 后台校验 | 无 | 目录级队列，限并发 2、条间隔 150ms、撞 503 冷却 5 分钟 |
| 目录级 TTL | 无 | **60 秒**，且跨进程持久化在 `folders.json.checked` |
| 状态点 | 每次 `list()` 都通知（会抖） | 只在离线态**真的翻转**时通知 |

### 改动的 9 个文件（382 增 / 65 删）

| 文件 | 改动 |
|---|---|
| `services/cache/cached-adapter.ts` | 主体：`list()` 本地优先 + `reconcile()` 对账 + 校验队列 + `subscribeData()`；`forget()` 摘整棵子树、`move()` 搬运整棵子树；新增浏览器 `online/offline` 信号 |
| `services/cache/meta.ts` | `folders.json` 多两列：`listed`（列过哪些目录）、`checked`（各目录上次校验时刻，留 10 分钟） |
| `services/cache/background.ts` | 「立即同步」把校验时刻全部作废，整棵树重新对账 |
| `storage/notes.ts` | ① 导出 `invalidateTree()`；② `tree()` 加 `treePending` 去重（列表与文件夹同时请求只走一遍）；③ 回收站正文改 `preferCache`；④ **修既有 bug**：`walkTree` 的 `frontier = next` 覆盖（见 §四） |
| `stores/sync.ts` | 新增 `dataVersion` + `subscribeData()` 接线（与状态点的 `subscribe()` 分开，否则成环） |
| `views/HomeView.vue` 等 4 个视图 | 各加一行 `watch(() => sync.dataVersion, load)` |

### 两个信号必须分开（本批次最容易踩的坑）

`markOnline()` 原来在每次 `list()` 结束时都会 `notify()`。如果把「视图重取数据」挂在这个通知上，
就会 `load → list → notify → load` 成环。所以拆成：

- `subscribe()` —— 状态点用（离线态 / dirty 数）；
- `subscribeData()` —— 视图用（云端数据真的变了），且 200ms 合并成一次通知。

## 二、请求量对比（同源假 WebDAV，5 目录 / 20 篇，观察窗 6 秒）

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 冷启动（无缓存） | 20 PROPFIND / 20 GET | **10 PROPFIND / 20 GET** |
| 冷启动（有缓存，校验已过期） | 20 PROPFIND / 0 GET | **10 PROPFIND / 0 GET** |
| 冷启动（有缓存，校验在 60 秒 TTL 内） | 20 PROPFIND / 0 GET | **0 PROPFIND / 0 GET** |
| 切页 → 文件夹 | 10 PROPFIND | **0** |
| 切页 → 回收站 | 1 PROPFIND | 1 |
| 切页 → 全部笔记 | 20 PROPFIND | **0** |

- 「改造前」列是在**同一套测量台**上、把 9 个文件回退后测的；为保持唯一变量，回退时**只保留 `walkTree` 那一行修复**。
- 改造后复测日志：`.workbuddy/tmp/donote/count-after-*.log`。
- 首屏（有缓存、TTL 内）**63ms** 就渲染出列表，且渲染发生在后台校验之前 —— 由 `cache-verify.cjs` 断言。

### ⚠️ 「冷启动 1 次请求」做不到，如实说明

目标里写的是「冷启动从 N 次降到 1 次」。实测发现 **坚果云把 `Depth: infinity` 静默降级成 `Depth: 1`**
（返回与 Depth:1 逐字节一致），没有「一次拿整棵树」的接口。所以：

- **能做到**：首屏 0 网络等待（列表立刻出）、TTL 内切页 0 请求、请求量减半；
- **做不到**：冷启动把请求压到 1 次。冷启动仍是「1 + 目录数」，只是全部挪到后台、用户看不见。

## 四、踩到的问题

### 1. 修正上一轮报告的结论：坚果云**文件**有真 etag

上一轮只探了 `Depth: 0` 的**根目录**（集合只回 `<d:getetag/>` 空元素），据此写下「不返回 etag」。
本轮实测：**文件**有 22 字符 base64url 的真 etag，**内容变 → etag 变**、**同内容重写 → etag 稳定**；
集合仍然没有；PUT 响应头不带 ETag。所以校验改成 **etag 优先、mtime 按秒兜底**，不用每次都重拉全文。

（`getlastmodified` 只到秒，本地写入给的是毫秒，混在一起比会让「刚写完的那篇」永远判为变了 → `sameSecond()` 压到秒。）

### 2. 既有 bug：同一层超过 4 个目录时，第 5 个起整棵子树被静默丢弃

`notes.ts` 的 `walkTree` 里 `frontier.splice(0, 4)` 每次只取走 4 个，下一轮却写 `frontier = next` ——
**剩下的待办被覆盖**。实测「项目/2025」「项目/2026」从来没被列出来过。改成 `frontier = frontier.concat(next)`。

> 这个 bug 也污染了最初的基线测量（改造前少算了一整棵子树的请求），所以基线是**单独重测**的。

### 3. 空缓存冷启动一度出现 72 次 PROPFIND

两个原因叠加：① `notesApi.list()` 与 `foldersApi.list()` 同时请求，各跑一遍目录树 → 加 `treePending` 去重；
② 上面的 `frontier` 覆盖 bug。修完 = 10 PROPFIND / 20 GET。

### 4. actions-e2e 的 2 项失败：定位为坚果云 503，**不是缓存回归**

症状：第 8 步「回收站里出现了它」「原位置已不在」双双失败 —— 软删没生效。
定位过程：把真实用例的整条链路（建笔记 + 附件目录 → 改名 → 移动进文件夹 → 重载 → 右键删除）
搬到**同源假 DAV** 上跑，走界面、走 API 都**全绿**；随后在「软删前置的那次 GET」上**注入一个 503**，
失败症状与真实用例**逐字一致**（回收站不变 + 原位置还在），并且 `notesApi.remove` 报
`读取笔记失败（HTTP 503）`。回归期间账号确实处于 `BlockedTemporarily`（探针实测）。

> 附带发现（**既有问题，本批次没动**）：软删的前置读一旦失败（503 等），删除整条动作直接中断，
> 界面看不到明显提示。要不要在后续批次里给它一个明确的失败反馈，等裁决。

### 5. 回收站没有再新建 `trash.json`

任务书写的是「缓存到 `data/cache/trash.json`」。实际**没建**：回收站条目在软删那一刻就已经
(`meta.json` 行 + `notes/.trash/*.md` 正文副本) 各留了一份，再加 `trash.json` 就是同一份数据的第三个副本。
回收站的列表与正文都直接复用现有两份，切到回收站依旧是 1 次 PROPFIND。**这一处按任务书口径算偏离，请裁决。**

## 八、附带的三个小修（2026-10-12，按核实结论定案）

核实文档 `docs/folder-note-model.md` §6 的三条待确认，用户已裁决并当场修掉（提交 `dacac3a` / `d8ff24f`）：

| 裁决 | 改动 |
|---|---|
| ② `note_count`（直系）与 `list({folder_id})`（含后代）口径不一致 = **bug** | `notesApi.list({folder_id})` 改成**只返回直系子级**，与 `FolderDTO.note_count` 一致 |
| ③ `foldersApi.create` 不查重 = **bug** | 与 `rename` 同一套 `uniqueRel`，撞名自动补「 2」后缀（原来 `mkdir` 把 405 当成功，会静默复用既有目录） |
| ⑤ 同名目录与笔记要能区分 | 目录加 📁 前缀、笔记加 📄 前缀（笔记卡片标题、文件夹行、两处文件夹选择器） |

### 顺带必须补的一处：`list(path, { fresh: true })`

③ 的查重和缓存层是**冲突**的 —— `uniqueRel` 拿到的目录列表是「本地优先」的，
用旧列表查重等于没查（别人在另一台设备建的同名笔记会被覆盖）。所以适配器 `list()` 多了一个 `fresh` 选项：

> **判据：这次列表的结果被用来决定「叫什么名字 / 会不会覆盖 / 要不要删」时用 `fresh`；
> 纯粹拿来显示的列表一律不传，仍走本地优先。**

用到 `fresh` 的地方：`uniqueRel`（新建重名检查）、`moveAssets` 的目标与来源（附件避让）、
`foldersApi.remove` 的子项列表（解散前点清里面有什么，否则会把没列到的内容一起删掉）。
写路径本来就是用户触发的低频操作，这里回到改造前的请求量，不构成额度负担。
