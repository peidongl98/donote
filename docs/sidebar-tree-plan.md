# 侧栏树形导航：请求量核实与落地方案

> 2026-10-12。任务 C1 的产物，用于回答一个问题：侧栏改成文件夹树之后，
> 数据要**全量拉整棵树**，还是**只拉展开的层**。
>
> 测量脚本 `.workbuddy/tmp/donote/cache-count.cjs`。做法：把同步根指向一个**同源**的假 WebDAV
> （`http://localhost:5173/davmock`，`page.route` 在浏览器层接住），数 PROPFIND 次数。
> 同源 → 不进 CORS、没有 OPTIONS 预检，数出来的就是业务请求；不碰坚果云、不耗限流额度。
>
> 复跑命令（`NODE_PATH` 指向 `…/node/workspace/node_modules`）：
> `node cache-count.cjs <标签> <cold-warm|pages|pages-cold> [顶层数] [每层子目录数]`
> 规模取 `3 2` = 10 个目录（根 + 3 顶层 + 3×2 子层，18 篇笔记）；取 `5 5` = 31 个目录（75 篇笔记）。

## 一、判据（任务书原文）

- 增加 **< 5** 请求 → 全量拉整棵树
- 增加 **> 10** 请求 → 只拉展开的层

「增加」= 侧栏常驻后的请求量 − 现在的请求量，**同场景、同目录规模**相比。

## 二、实测结果

数字是 PROPFIND 次数（不是字节数）。

| 场景 | 10 目录 | 31 目录 |
|---|---|---|
| 首屏 `/`（目录缓存过期 → 整树重新校验） | **10** | **31** |
| 笔记详情（目录缓存新鲜） | 1 | 1 |
| 回收站（目录缓存新鲜） | 1 | 1 |
| 设置（目录缓存新鲜） | 1 | 1 |
| 笔记详情（目录缓存**过期**） | **11** | **32** |
| 回收站（目录缓存过期） | 1 | 1 |
| 设置（目录缓存过期） | 1 | 1 |

> GET 列没有被用作判据，也不该用：它数的是摘要补齐（列表要显示摘要，而 WebDAV 列目录不含正文）
> 时的正文读取，属**异步、按需**，跑没跑到全看采样窗口 —— 同一场景两次实测分别是 0 与 37。
> 目录树的成本只体现在 PROPFIND 上。

### 三条事实

1. **一次完整目录遍历 = 目录数（含根）次 PROPFIND。**
   `walkTree()`（`apps/web/src/storage/notes.ts:120-151`）对每个目录发一次 `Depth: 1`；
   `Depth: infinity` 被坚果云降级成 1（见 `batch4-report.md`），所以「一个请求拉整棵树」做不到。
   10 目录 10 次、31 目录 31 次，与「目录数」严格吻合。
2. **首屏 `/` 本来就要走完这棵树** —— 笔记列表要拿全部笔记。笔记详情页也走（面包屑要算所属文件夹），
   读数 = 目录数 + 该页自身 1 次。回收站与设置两页**完全不碰**目录树，各自那个 1 次是自己的目录列举。
3. **`tree()` 只有一份。** 模块级 3 秒缓存（`treeCache`）+ 并发合并（`treePending`）在
   `storage/notes.ts:154-176`；`notesApi.list()` 与 `foldersApi.list()` 都调它 → 同一次页面加载里
   两个调用方共用**一次**遍历，不会各走一遍。

### 「侧栏常驻后」是怎么得出的

侧栏还没实现，没法直接测。但侧栏要的两样东西——
文件夹的父子关系（`foldersApi.list()`，`storage/notes.ts:580-603`）与每个文件夹下的笔记
（`notesApi.list()`）——**都走 `tree()`**，而 `treeCache` / `treePending` 会把它们并成一次遍历，
且首屏那次遍历本来就会发生（事实 2）。

→ 侧栏常驻带来的增量**由代码结构决定，是 0**，不是估计。

## 三、结论：全量拉整棵树

> **裁决已定（2026-10-12，用户）**：侧栏树数据取法 = **全量拉整棵树**。
> 理由（用户给的）：① 有缓存层兜底（TTL 60 秒内切页 0 请求）；② 侧栏是常驻 UI，
> 懒加载会造成「点一下等一次」；③ 实现简单 —— 懒加载要处理展开时异步加载、
> 加载失败重试、并发展开等边界，容易出 bug。
>
> ⚠️ 用户同批给的第四条理由「`walkTree` 每层 1 次 PROPFIND → 典型 3-5 层 = 3-5 个请求」
> **与实测不符**：`walkTree` 是**每目录** 1 次（`Depth: 1`），10 目录 = 10 次、31 目录 = 31 次
> （原因见下面事实 1：`Depth: infinity` 被坚果云降级成 1，所以只能逐目录走）。
> 用户另设的保护条件「≤ 8 按全量实现 / > 15 停下汇报」因此被触发，已汇报。

| 场景 | 现在 | 侧栏常驻后 | 增加 | 判据落点 |
|---|---|---|---|---|
| 首屏 `/`，10 目录 | 10 | 10 | **0** | < 5 → 全量 |
| 首屏 `/`，31 目录 | 31 | 31 | **0** | < 5 → 全量 |
| 笔记详情，10 / 31 目录 | 11 / 32 | 11 / 32 | **0** | < 5 → 全量 |
| 回收站 / 设置，10 目录 | 1 | 10 / 31〔推算〕 | **+9** | 落在 5–10 的灰区 |
| 回收站 / 设置，31 目录 | 1 | 10 / 31〔推算〕 | **+30** | > 10 → 只拉展开的层 |

**选「全量」，理由是判据在首屏这一档上是干净的**（+0，10 与 31 目录都一样），
而首屏是侧栏主要出现的位置。任务书列的第一个测量项也正是「现有冷启动请求量」= 首屏。

反过来看「只拉展开的层」为什么不选：

1. 它会**再实现一套逐层列举**（`listDir` 现在是 `storage/notes.ts` 的私有函数，要新开公开 API），
   而 `tree()` 已经在做同一件事——两套机制各自维护缓存与失效，属「同一信号上叠多层派生状态」。
2. 它要**给每个展开节点配 loading / 失败态**，并且 `dataVersion` 变化后要重拉**所有已展开路径**；
   全量方案只需重取一次被缓存的 `tree()`。
3. 「当前笔记高亮」要求祖先链可见；懒加载下要么高亮不到，要么自动展开祖先（+depth 次请求，而
   `MAX_DEPTH = 8`）。全量方案天然可见。
4. 首屏这个最常见的入口，懒加载反而**先多拉一次根层**（全量方案的根层请求已被首屏那次遍历覆盖）。

### 已知代价（写在这里，不藏）

- **冷启动直接落在 `/trash` 或 `/settings`** 时，侧栏会新付一次整树遍历（= 目录数 − 1 次，
  10 目录 +9、31 目录 +30）。这是**推算**（依据是事实 1 的「一次遍历 = 目录数」），侧栏实现后应复测。
  实际影响：一次性成本，之后 60 秒内（目录缓存的 TTL）在任何页面都复用，且用户从 `/` 进站的常规路径本就付过。
- **移动端抽屉关闭时不渲染树**（沿用现有 `v-if="layout.open"` 语义），否则手机冷启动会白付一次遍历。
- `walkTree` 有 `MAX_DIRS = 300` / `MAX_DEPTH = 8` 的护栏（`storage/notes.ts:116-117`）。
  全量方案下，超过 300 个目录的网盘会让侧栏树**提前截断**（与列表页现在被截断是同一处上限）。
  私有笔记库一般远低于这个量级；真要越过再谈懒加载。

## 四、C2 的落地点（与任务书结构一一对应）

| 要求 | 落法 |
|---|---|
| 260px 可折叠 | 已有：`--sidebar-w` + `html[data-sidebar]`，`stores/layout.ts` 不动 |
| 文件夹树缩进 `depth × 18px` | 与 `/folders` 页（`FoldersView.vue`）同口径 |
| 点文件夹行展开折叠 | 行左侧「▸/▾」按钮切换 `expanded` |
| 点名字跳 `/folders/:id` | `router.push('/folders/' + folder.id)` |
| 点笔记跳 `/notes/:id` | 同上 |
| 当前笔记高亮 | `route.path === '/notes/' + note.id` |
| 悬停「+」「⋯」 | 行内右侧按钮，`+` 在该文件夹下新建笔记，`⋯` 复用现有菜单能力 |
| 展开状态存 localStorage | key `donote.sidebar.expanded`（存 folder id 数组） |
| 图标 📁 / 📄，根节点无图标 | 与 `NoteCard.vue:93,97`、`FoldersView.vue:279` 现用的一致 |
| 数据与刷新 | `foldersApi.list()` + `notesApi.list({ limit: 100_000 })`（沿用 `stores/sync.ts` 的写法），层级用 `parent_id` / `parentOf()` 现算分组，**不新增遍历**；`watch(() => sync.dataVersion, load)` |

三个会踩的点：

1. `foldersApi.list()` 返回的是**扁平** `FolderDTO[]`（`id` = base64url(路径)、`parent_id`、`name`、`note_count`），
   不是树。「树」要靠 `parent_id` 现算，别指望数据层给出层级。
2. `.rail` 是 `z-index: 20`，在已理清的层级栈里位于 `NoteActionMenu .sheet-mask`(21) 与 `AppDialog .mask`(22)
   **之下**。侧栏内的悬停菜单若是 `fixed` 全屏弹层，会盖住这两者 —— 用贴着行的 popover，不要用 `.sheet`。
   另外 `styles/glass.css` 有一条全局 `.glass > * { position: relative; z-index: 2 }`，
   行内绝对定位的悬停按钮 z-index 要 > 2（`NoteCard.vue` 的 `.pick` 踩过同一个坑）。
3. `.sheet` / `.sheet-mask` 目前是 `FoldersView.vue` 的 scoped 样式（`app.css` 里没有），
   侧栏要用得自己写，或先提到全局。

## 五、自检

**可行。** 数据层零改动：不新增 API、不新增遍历，`tree()` 一份缓存供列表页与侧栏共用。
